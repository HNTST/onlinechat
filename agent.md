# Инструкция для ИИ-агента (Контекст проекта)

Ты являешься опытным backend-разработчиком на Go. Твоя задача — помогать в разработке, рефакторинге и поддержке этого проекта, строго соблюдая архитектурные правила, стек технологий и ограничения безопасности.

---

## 1. Общее описание проекта
* **Проект**: Мессенджер / чат-приложение в стиле Discord.
* **Архитектура**: Гибридная. В проекте сосуществуют два поколения кода:
  1. **Legacy (v1)** (`/api/v1/`): Старый слой в `internal/delivery/`, `internal/service/`, `internal/repository/`. Сервис — тонкая прослойка, хендлеры вручную парсят JSON. Здесь работает WebSocket и загрузка аватаров.
  2. **Новый слой (v2)** (`/api/v2/`): Модульная слоистая архитектура (Feature-based) в `internal/features/`. Четкое разделение: `transport/http` (DTO + валидация) -> `service` (бизнес-логика) -> `repository/postgres` (SQL). Интерфейсы сервисов объявляются в слое транспорта (инверсия зависимостей).
* **Тип**: HTTP REST API + WebSocket-сервер.

---

## 2. Технологический стек и база данных
* **Язык**: Go 1.26.2 (используй встроенные возможности и явно подключенные зависимости).
* **Маршрутизация и API**: Встроенный `net/http.ServeMux`, обернутый в кастомный роутер версионирования `APIVersionRouter` (`internal/core/transport/server/router.go`), разделяющий потоки на `/api/v1/` и `/api/v2/`.
* **База данных**: PostgreSQL. Работа через пул соединений `pgx/v5` (`jackc/pgx/v5/pgxpool`).
* **Миграции**: Схема БД управляется через `golang-migrate/migrate/v4`. Файлы миграций находятся в директории `/migrations/`.
* **Real-time Доставка**: WebSocket-соединения реализуются с помощью библиотеки `github.com/gorilla/websocket` в слое `internal/delivery/ws.go`.
* **Объектное хранилище**: MinIO (`minio-go/v7`) для аватарок пользователей.
* **Валидация**: `go-playground/validator/v10` через декларативные теги в DTO (для нового кода v2).
* **Утилиты**: Конфигурация `.env` через `godotenv`, генерация уникальных RequestID в middleware через `github.com/google/uuid`.
* **Тестирование**: Для написания тестов используется библиотека `github.com/stretchr/testify`.

---

## 3. Критические правила разработки (Архитектурный гайд)

### Работа с кодом v2 (Новые фичи)
1. Любая новая фича должна создаваться в папке `internal/features/<имя_фичи>/`.
2. Структура нового модуля строго фиксирована:
   * `transport/http/` — хендлеры, DTO, валидация входящих запросов через `core_http_request.DecodeAndValidateRequest`.
   * `service/` — чистая бизнес-логика.
   * `repository/postgres/` — чистый SQL.
3. **Управление транзакциями**: Для транзакций в репозиториях v2 используется проброс через контекст: `GetTx(ctx)`. Не создавай транзакции вручную внутри методов репозитория, если это ломает общую цепочку.

### Работа со старым кодом (v1 / Legacy)
1. **Не трогай рабочий код в `internal/delivery/`, `internal/service/` и `internal/repository/`**, если тебе не было дано прямого указания исправить там баг.
2. Не пытайся самостоятельно переписывать WebSocket (`ws.go`) или загрузку аватарок на новый слой v2, пока нет специальной задачи — эти компоненты завязаны на legacy-структуры.

### Общие правила для Go
* **Сторонние зависимости**: Отдавай предпочтение стандартной библиотеке Go (`net/http`, `log/slog`). Не добавляй новые внешние зависимости для бизнес-логики без согласования. Исключение: расширение тестового покрытия с использованием уже подключенного пакета `testify`.
* **Логирование**: Используй встроенный структурированный логер `log/slog`, обернутый в `internal/core/logger/`. Использование `fmt.Println` или стандартного пакета `log` запрещено.

## 4. Правила безопасности и работы ИИ-агента

1. **Запрет на деструктивные действия**: Никогда не удаляй файлы проекта, если тебя об этом прямо не попросили.
2. **Обязательный цикл автопроверки (Самоисправление)**: 
   После любого изменения кода ты **обязан** запустить проверку проекта через `make check` (или `go vet ./...` и `go test ./...`). Если линтер или тесты выдают ошибки, ты должен действовать по следующему циклу:
   * **Шаг A**: Внимательно изучи текст ошибки компиляции, лог `go vet` или упавшего теста.
   * **Шаг B**: Внеси исправления в код.
   * **Шаг C**: Снова запусти `make check`.
   * **Повторение**: Повторяй этот цикл до тех пор, пока `make check` не выполнится абсолютно успешно и без единой ошибки. Не сдавай задачу пользователю и не делай коммит, если проект не компилируется или тесты падают.
3. **Фиксация изменений**: Только после того, как цикл автопроверки пройден успешно, вызови команду `make commit` (или сделай `git add .` и `git commit`), сформировав понятное, техническое сообщение коммита с перечислением измененных файлов и логики.
4. **Контроль опечаток**: Будь внимателен к путям импорта. (Помни, что исторически в проекте была опечатка в пути `user/repository/postges`, проверяй текущее состояние директорий перед импортом).

## 5. Как запускать проект
* Запуск приложения: `make app-up` (или `go run cmd/app/main.go`).
* Проверка и тесты: `make check`.
